# terraria-piscatio-automatica

Inject-DLL авторыбалки для Terraria **1.4.5.8** (x86, .NET Framework + XNA).
В PE-ресурсе стоит 1.4.5.6, но сборка и `Main.versionNumber` дают 1.4.5.8.
Инжектор внешний и любой — здесь только DLL.

## Статус

DLL инжектится, цепляется к CLR, читает живое состояние рыбалки и рисует
поверх игры панель состояния. Забросом пока не управляет — это следующий этап.

| Этап | Что | Состояние |
|---|---|---|
| 1 | CLR-рефлексия, лог, конфиг, хоткеи | готово |
| 3 | Оверлей: хук `EndScene`, панель состояния | готово |
| 2 | Детур `Player.ItemCheck`, автомат заброса и подсечки | дальше |
| 3б | Родные ассеты и шрифт Terraria вместо системного | |
| 4 | Автопитьё зелий | |

## Сборка

```bash
cargo build --release
```

Таргет `i686-pc-windows-msvc` прибит в `.cargo/config.toml`: Terraria всегда
32-битная (`32BITREQUIRED` в CLR-заголовке), 64-битная DLL в неё не встанет.

Результат: `target/i686-pc-windows-msvc/release/piscatio.dll`

## Инжект

Контракт универсальный, любой инжектор подойдёт:

- обычный **LoadLibrary**-инжект (Extreme Injector v3 и подобные) — работает
  через `DllMain`, ничего настраивать не нужно;
- **manual-map** — если инжектор не зовёт `DllMain`, вызови экспорт `Start`.
  Экспорт `Stop` останавливает рабочий поток, не выгружая модуль.

Инжектить **после загрузки главного меню**: до этого CLR ещё не подняла сборку
Terraria. Если инжектировать раньше, DLL сама подождёт — 40 попыток по 750 мс.

## Хоткеи

| Клавиша | Действие |
|---|---|
| `Стрелка вверх` | показать/скрыть UI (появится на этапе 3) |
| `Стрелка вниз` | старт/стоп рыбалки |
| `Delete` | выгрузить DLL |

Переназначаются в `piscatio.toml` через виртуальные коды клавиш.

Выгрузка по `Delete` работает только при LoadLibrary-инжекте: при manual-map
модуля в списке загруженных нет, и `FreeLibrary` неприменим — поток просто встанет.

## Файлы рядом с DLL

- `piscatio.log` — лог. При manual-map своей папки у DLL нет, тогда лог ляжет
  рядом с игрой.
- `piscatio.toml` — конфиг, создаётся при первом запуске.

Ключевые настройки:

```toml
filter_mode = "blacklist"     # blacklist | whitelist
blacklist = [2337, 2338, 2339]  # Old Shoe, Seaweed, Tin Can
pull_enemy_spawns = false     # подсекать ли Дюка Фишрона и прочее
quick_stack_when_full = true  # инвентарь полон -> разложить по сундукам
disable_inactive_throttle = true
```

`disable_inactive_throttle` снимает `Main.ThrottleWhenInactive`. Без этого
свёрнутая игра спит по 20 мс на кадр и рыбалка идёт заметно медленнее.

## Что должно быть в логе на этапе 1

```
шаг 3: CLR v4.0.30319 — дефолтный AppDomain получен
шаг 4: сборка найдена — Terraria, Version=1.4.5.8, ...
шаг 5: типы Main/Projectile/Player/Item получены
шаг 6: все поля и методы разрешены
версия игры: v1.4.5.8
ThrottleWhenInactive снят — свёрнутая игра не будет спать
поплавка нет. наживка=..., свободных слотов=...
поплавок #1: ai[0]=0 ai[1]=0 localAI[1]=317
поклёвка: localAI[1]=2290 (предмет), ai[1]=-181 -> подсекаем
```

Строка «поклёвка» — главная проверка этапа: она означает, что мы видим улов
**до** подсечки и можем решать, тянуть его или пропустить.

**Для неё нужна наживка в инвентаре.** Без наживки `TryBuildFishingContext`
не собирает контекст, улов не прокатывается, и `ai[1]` навсегда остаётся 0 —
в логе видно только, как `localAI[1]` накапливается до 660 и сбрасывается.

## Как это устроено

Terraria — managed-процесс, поэтому вместо офсетов и паттерн-сканов DLL цепляется
к уже поднятой CLR (`ICorRuntimeHost` → дефолтный AppDomain) и идёт по цепочке
рефлексии `_AppDomain` → `_Assembly` → `_Type` → `_FieldInfo`.

Вызовы делаются по номерам слотов vtable, снятым из `mscorlib.tlb`, а не через
`IDispatch` — late binding у CLR не работает, см. «Известные грабли». На главное
свойство это не влияет: типы, поля и методы по-прежнему ищутся **по именам**
(`Type.GetField("myPlayer")`), поэтому патчи игры ломают код только при
переименовании полей. Слоты же принадлежат .NET Framework, чей API заморожен.

Механика рыбалки разобрана по декомпиляции — см.
[docs/research-1.4.5.6.md](docs/research-1.4.5.6.md).

## Известные грабли

- **`ICorRuntimeHost` в windows-rs 0.62.2 объявлен с чужим IID** — там стоит
  `IID_ICorThreadpool`. Любой `GetInterface` с ним возвращает `E_NOINTERFACE`.
  Раскладка vtable при этом верная, поэтому интерфейс запрашивается вручную
  с настоящим IID из `mscoree.h` (см. `src/clr.rs`).
- **Late binding через `IDispatch` к CLR неприменим.** Проверено на живой
  CLR v4.0.30319: объект хостинга AppDomain не отдаёт `IDispatch` вообще
  (`E_NOINTERFACE`), у `_AppDomain` слоты IDispatch — заглушки `E_NOTIMPL`,
  а `System.Type` (RuntimeType) тоже без `IDispatch`. Работает только
  типизированный vtable, слоты сняты из `mscorlib.tlb`.
  Исключение — `_Assembly`: у него `IDispatch` есть, но он не нужен.
- **`_AppDomain::GetDefaultDomain` требует предварительного `Start()`**,
  иначе `E_UNEXPECTED`. В игре рантайм уже запущен, но вызов оставлен
  на случай инжекта до старта CLR.
- **`Type.GetMethod(String)` бросает `AmbiguousMatchException`** на
  перегруженных методах. Годится только для уникальных имён вроде
  `QuickStackAllChests`.
- Managed-массивы маршалятся в SAFEARRAY (`Projectile[]` -> `VT_ARRAY|VT_UNKNOWN`,
  `float[]` -> `VT_ARRAY|VT_R4`), поэтому индексируются напрямую,
  без рефлексии.
- Пересобрать DLL, пока она загружена в запущенную игру, нельзя — файл занят.
  Закройте игру либо переименуйте занятый файл: Windows разрешает переименование
  замапленной DLL, и сборка пройдёт.
