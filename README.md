# terraria-piscatio-automatica

Inject-DLL авторыбалки для Terraria **1.4.5.8** (x86, .NET Framework + XNA).
В PE-ресурсе стоит 1.4.5.6, но сборка и `Main.versionNumber` дают 1.4.5.8.
Инжектор внешний и любой — здесь только DLL.

## Статус

DLL инжектится, цепляется к CLR, читает живое состояние рыбалки, рисует
поверх игры панель родным шрифтом и управляет забросом с подсечкой.

| Этап | Что | Состояние |
|---|---|---|
| 1 | CLR-рефлексия, лог, конфиг, хоткеи | готово |
| 3 | Оверлей: хук `EndScene`, панель состояния | готово |
| 2 | Детур `Player.ItemCheck`, автомат заброса и подсечки | на тесте |
| 3б | Родной шрифт Terraria из `Mouse_Text.xnb` | готово |
| 4 | Автопитьё зелий | |

## Сборка

```bash
cargo build --release
```

Таргет `i686-pc-windows-msvc` прибит в `.cargo/config.toml`: Terraria всегда
32-битная (`32BITREQUIRED` в CLR-заголовке), 64-битная DLL в неё не встанет.

Результат: `target/i686-pc-windows-msvc/release/piscatio.dll`

## Инжект

Контракт универсальный, любой инжектор подойдёт:

- обычный **LoadLibrary**-инжект (Extreme Injector v3 и подобные) — работает
  через `DllMain`, ничего настраивать не нужно;
- **manual-map** — если инжектор не зовёт `DllMain`, вызови экспорт `Start`.
  Экспорт `Stop` останавливает рабочий поток, не выгружая модуль.

Инжектить **после загрузки главного меню**: до этого CLR ещё не подняла сборку
Terraria. Если инжектировать раньше, DLL сама подождёт — 40 попыток по 750 мс.

## Как ловит

Первый заброс делаешь сам — из него запоминается точка прицела (экранные
координаты). Дальше автомат:

- поплавка нет -> заброс в ту же точку;
- поклёвка, улов проходит фильтр -> подсечка;
- поклёвка, улов не проходит -> ничего, игра сама сбросит,
  **наживка при этом не тратится**;
- наживка кончилась -> стоп;
- инвентарь полон -> `QuickStackAllChests`, если включено.

Выключение рыбалки сбрасывает точку прицела: следующий ручной заброс задаст
новую. Задержки с разбросом из `jitter_min_ms` / `jitter_max_ms`.

Нажатие не эмулируется через `SendInput` — при свёрнутом окне игра реальный
ввод игнорирует. Вместо этого детур `Player.ItemCheck` выставляет
`Player.controlUseItem` прямо внутри игрового кадра.

## Хоткеи

| Клавиша | Действие |
|---|---|
| `Стрелка вверх` | показать/скрыть панель оверлея |
| `Стрелка вниз` | старт/стоп рыбалки |
| `Delete` | выгрузить DLL |

Переназначаются в `piscatio.toml` через виртуальные коды клавиш.

Выгрузка по `Delete` работает только при LoadLibrary-инжекте: при manual-map
модуля в списке загруженных нет, и `FreeLibrary` неприменим — поток просто встанет.

## Файлы рядом с DLL

- `piscatio.log` — лог. При manual-map своей папки у DLL нет, тогда лог ляжет
  рядом с игрой.
- `piscatio.toml` — конфиг, создаётся при первом запуске.

Ключевые настройки:

```toml
filter_mode = "blacklist"     # blacklist | whitelist
blacklist = [2337, 2338, 2339]  # Old Shoe, Seaweed, Tin Can
pull_enemy_spawns = false     # подсекать ли Герцога Рыброна и прочих врагов
quick_stack_when_full = true  # инвентарь полон -> разложить по сундукам
disable_inactive_throttle = true
```

`disable_inactive_throttle` снимает `Main.ThrottleWhenInactive`. Без этого
свёрнутая игра спит по 20 мс на кадр и рыбалка идёт заметно медленнее.

## Что должно быть в логе на этапе 1

```
шаг 3: CLR v4.0.30319 — дефолтный AppDomain получен
шаг 4: сборка найдена — Terraria, Version=1.4.5.8, ...
шаг 5: типы Main/Projectile/Player/Item получены
шаг 6: все поля и методы разрешены
версия игры: v1.4.5.8
ThrottleWhenInactive снят — свёрнутая игра не будет спать
поплавка нет. наживка=..., свободных слотов=...
поплавок #1: ai[0]=0 ai[1]=0 localAI[1]=317
поклёвка: localAI[1]=2290 (предмет), ai[1]=-181 -> подсекаем
```

Строка «поклёвка» — главная проверка этапа: она означает, что мы видим улов
**до** подсечки и можем решать, тянуть его или пропустить.

**Для неё нужна наживка в инвентаре.** Без наживки `TryBuildFishingContext`
не собирает контекст, улов не прокатывается, и `ai[1]` навсегда остаётся 0 —
в логе видно только, как `localAI[1]` накапливается до 660 и сбрасывается.

## Как это устроено

Terraria — managed-процесс, поэтому вместо офсетов и паттерн-сканов DLL цепляется
к уже поднятой CLR (`ICorRuntimeHost` → дефолтный AppDomain) и идёт по цепочке
рефлексии `_AppDomain` → `_Assembly` → `_Type` → `_FieldInfo`.

Вызовы делаются по номерам слотов vtable, снятым из `mscorlib.tlb`, а не через
`IDispatch` — late binding у CLR не работает, см. «Известные грабли». На главное
свойство это не влияет: типы, поля и методы по-прежнему ищутся **по именам**
(`Type.GetField("myPlayer")`), поэтому патчи игры ломают код только при
переименовании полей. Слоты же принадлежат .NET Framework, чей API заморожен.

Панель рисуется родным шрифтом игры: `Content/Fonts/Mouse_Text.xnb`
распаковывается (LZX), нужные глифы вынимаются из DXT3-страниц и
переупаковываются в один атлас. Если файла нет — откат на системный
шрифт через GDI.

Механика рыбалки разобрана по декомпиляции — см.
[docs/research-1.4.5.6.md](docs/research-1.4.5.6.md).

## Известные грабли

- **`ICorRuntimeHost` в windows-rs 0.62.2 объявлен с чужим IID** — там стоит
  `IID_ICorThreadpool`. Любой `GetInterface` с ним возвращает `E_NOINTERFACE`.
  Раскладка vtable при этом верная, поэтому интерфейс запрашивается вручную
  с настоящим IID из `mscoree.h` (см. `src/clr.rs`).
- **Late binding через `IDispatch` к CLR неприменим.** Проверено на живой
  CLR v4.0.30319: объект хостинга AppDomain не отдаёт `IDispatch` вообще
  (`E_NOINTERFACE`), у `_AppDomain` слоты IDispatch — заглушки `E_NOTIMPL`,
  а `System.Type` (RuntimeType) тоже без `IDispatch`. Работает только
  типизированный vtable, слоты сняты из `mscorlib.tlb`.
  Исключение — `_Assembly`: у него `IDispatch` есть, но он не нужен.
- **`_AppDomain::GetDefaultDomain` требует предварительного `Start()`**,
  иначе `E_UNEXPECTED`. В игре рантайм уже запущен, но вызов оставлен
  на случай инжекта до старта CLR.
- **`Type.GetMethod(String)` бросает `AmbiguousMatchException`** на
  перегруженных методах. Годится только для уникальных имён вроде
  `QuickStackAllChests`.
- Managed-массивы маршалятся в SAFEARRAY (`Projectile[]` -> `VT_ARRAY|VT_UNKNOWN`,
  `float[]` -> `VT_ARRAY|VT_R4`), поэтому индексируются напрямую,
  без рефлексии.
- **Панель рисуется из детура `Main.DrawCursor`, а не из `Present`.** Игра
  зовёт `DrawCursor` первым делом после `spriteBatch.End()`: весь интерфейс
  уже выгружен на экран, а курсор ещё не нарисован. Панель, вставленная сюда,
  ложится поверх интерфейса и **под** курсор игры — своего рисовать не нужно.
  `Present` остаётся запасным путём: если детур не встал или игра в этом кадре
  курсор не рисовала (`Main.cursorOverride != -1`), панель уходит туда, и
  курсор дорисовывается сам. Флаг «уже нарисовано» гасится в `Present`,
  поэтому кадр без детура не пропадает.
- **Рисовать из `Present` надо, а не из `EndScene`.** Terraria рендерит
  в несколько проходов через render target'ы, `EndScene` вызывается по
  нескольку раз за кадр. Отрисовка там попадает в промежуточные цели, и игра
  потом использует их как текстуры — панель размножается по деревьям и воде.
  `Present` вызывается один раз за кадр и уже по финальной цели; сцену
  для своей отрисовки открываем сами. Из детура `DrawCursor`, наоборот, мы
  внутри чужой сцены — `BeginScene` там вернёт ошибку, и это нормально:
  `EndScene` тогда звать нельзя.
- **Оформление панели — родные текстуры игры, а не подобранные заливки.**
  Окна собираются девятичастной нарезкой `UI/PanelBackground` +
  `UI/PanelBorder` (12 + 4 + 12 = 28 пикселей, ровно как в `UIPanel`),
  строки — `UI/InnerPanelBackground`, кнопки — `UI/ButtonBacking`,
  переключатели — две половинки `UI/Settings_Toggle` (кольцо и диск),
  ячейки — `Inventory_Back`. Смысл ячейки показывается сменой текстуры
  (`Inventory_Back3` зелёная, `Inventory_Back5` красная), а не тонировкой:
  умножение цветом может только затемнить, и тёмно-синяя ячейка превращается
  в грязь. Цвет фона окна — `new Color(63, 82, 151) * 0.7f` из `UIPanel`,
  прозрачность берётся оттуда же.
- **`IntPtr` из рефлексии приезжает как `VT_INT` (22 = 0x16), а не
  `VT_INT_PTR` (37).** Это касается и `RuntimeMethodHandle.GetFunctionPointer()`,
  то есть адреса JIT-кода для managed-детура.
- **Порядок снятия оверлея важен.** Сначала гасить отрисовку, только потом
  освобождать ресурсы: иначе кадр между освобождением и снятием хуков
  успевает создать их заново, новая пара из `D3DPOOL_DEFAULT` остаётся висеть
  и запрещает устройству `Reset`. Игра после этого падает при сворачивании
  с `ObjectDisposedException: RenderTarget2D` — XNA освобождает свои
  render target'ы, а пересоздать их уже не может.
- **Перед выгрузкой DLL детуры обязательно снимать.** Иначе следующий кадр
  прыгнет по адресу уже отображённого кода — игра падает. По той же причине
  ресурсы оверлея держатся сырыми указателями без `Drop`: TLS-деструктор
  в выгруженном модуле уронил бы игру при выходе.
- **Шрифт Terraria — не стоковый XNA `SpriteFont`.** Это
  `ReLogic.Graphics.DynamicSpriteFontReader`: `float spacing`, `int lineSpacing`,
  `char defaultCharacter`, `int pageCount`, затем на каждую страницу
  Texture2D + четыре списка. Страниц полторы сотни, текстуры в DXT3.
  Формат сверен по декомпиляции ReLogic.dll из ресурсов Terraria.exe.
- **Подмена слота в vtable пробного девайса на D3D9 не работает.** Замерено
  на живой игре: vtable девайса лежит в куче (`0x1D166C9C`), а не в образе
  `d3d9.dll` (`0x68840000-0x689BA000`) — таблица своя на каждый девайс.
  Поэтому оверлей ставит inline-детур на саму функцию `EndScene` в коде
  `d3d9.dll`: реализация общая для всех девайсов.
- **Читать vtable нужно, пока девайс жив.** Таблица в куче освобождается
  вместе с девайсом, и чтение после `Release` — use-after-free. Проявляется
  не сразу: первый запуск может «сработать» на ещё не затёртой памяти.
- `retour` 0.3.1 не собирается под i686 на rustc 1.97 (`extern "win64"`),
  поэтому детуры делает `minhook`.
- Пересобрать DLL, пока она загружена в запущенную игру, нельзя — файл занят.
  Закройте игру либо переименуйте занятый файл: Windows разрешает переименование
  замапленной DLL, и сборка пройдёт.
